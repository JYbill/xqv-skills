# coding-with-plan

## 输入与分工

执行用户已确认的 plan，不重新规划或审批，不额外增加权限确认；遵守现有授权。Plan 路径无法唯一确定时先询问，不自行选择。

主 Agent 读取 plan、目标项目适用的 `AGENTS.md` 及其指向的开发、测试文档和模块说明；存在适用的 `CONTEXT-MAP.md` 或 `CONTEXT.md` 时一并加载。Review Agent 也读取相关原文，不只依赖摘要。

- **主 Agent**：负责实现、测试、自验、处理用户调整、修复评审问题和最终交付。
- **Review Agent**：独立、只读评审实现、测试及验证记录，向主 Agent 反馈问题，不直接修改文件，也不继续委派。

默认只创建一个 Review Agent，不另起 Coding 或 Test Agent。编码任务可拆成能并行推进的部分，且符合用户和项目授权时，允许主 Agent 创建多个 Coding 子 Agent。派发时明确各自的任务范围、文件归属和接口约定，避免同时修改同一文件；各子 Agent 负责所分配部分的实现与自验，主 Agent 负责整合、跨部分验证和最终交付。同一批文件尽量由一个会话修改。子 Agent 默认继承主 Agent 的模型配置，用户另有指定时遵从指定。

## 开工与验收范围

记录工作区、实现范围、评审起点和已有未提交改动，保留用户改动及暂存状态。确认独立评审所需协作工具实际可用，不能只凭配置判断；缺少必要资料或能力时按阻塞规则处理。

依据计划、改动范围和项目规范，一次明确本轮必需验收项及交付条件，简要记录在现有计划或工作记录中即可：

- 相关测试和静态检查，以及需要扩大检查范围的条件。
- 涉及批量处理时，确定数据规模和必要的性能验证；不凭测试通过推断性能达标。
- 使用原始 SQL 时，说明使用原因及项目要求的依据。
- 需要同步的规格、使用说明和完成状态。

只保留适用项，不默认增加全量检查、性能测试或新的记录文件。后续需求变化或新缺陷确实影响验收时再调整，不能降低既定要求。

## 实现与首次交接

主 Agent 按计划实现并同步完成依据和记录：写原始 SQL 时记录原因，涉及批量处理时按确定的规模验证，功能完成时同步对应规格。记录位置和详细程度遵守目标仓库规则，不把某个项目的要求套给所有任务。

普通编译或测试失败由主 Agent 继续定位、修复。首次交给 Review 前，统一核对实际 diff、验收项、实际验证命令和结果、验证对应的代码版本，以及未验证事项和原因。可预见的必要项应在此时齐全，避免测试通过后零散追加；无法完成的必要验证按阻塞处理，不能以“未验证”代替验收。

就绪后用 `spawn_agent` 创建 Review Agent，一次提供：

- plan 路径、工作区、规范入口、实现范围、评审起点和已有改动说明。
- 本 skill 规则、主 Agent 标识、待评审版本与实际 diff 的定位方式。
- 验收项、验证命令及结果、对应版本、未验证事项及原因。

版本可用提交标识结合未提交 diff 快照等方式定位，不要求为评审提交代码；仅有 `r1` 等标签不足以证明内容一致。评审期间主 Agent 避免修改待评审文件；收到用户调整时先核对影响，必要时中断受影响的评审，完成调整和适用验证后再交接。

## 独立评审与返工

Review 对照计划、开发和测试规范，检查验收覆盖、回归风险、测试有效性及必要依据；核对实际验证命令、结果与待评审版本，不能只凭“测试已通过”验收。问题需写明位置、计划或规范依据、影响和修复验收条件，区分必须修复与可选建议；个人偏好不能阻止通过。

Review 将结论交给主 Agent。主 Agent 修复必须处理的问题，按影响选择验证范围：

- **行为变化**：重跑受影响测试和必要检查；涉及共享行为或项目规范要求时扩大范围。
- **仅注释或文档变化**：检查对应内容、格式和链接，不重复整套行为测试；若发现其反映了实现缺陷，按实际行为影响处理。

修复完成后向同一个 Review Agent 提供问题处理结果、实际差异和新增验证记录。复审检查原问题是否解决及修复是否引入新问题，未受影响且仍有效的证据继续使用。必要的新缺陷仍须修复，不得通过改写已确认计划、降低测试要求或放宽断言消除问题。

## 协作与外部变化

- 用 `followup_task` 派发复审或需要回应的补充判断；`send_message` 仅用于通知，不会启动空闲 Agent。通信使用工具返回的完整 Agent 标识，不自行拼接。
- 同一交接只派发一次，反馈对应明确版本；忽略已处理或过时消息，状态不明时核实实际任务和差异，不重复派发。
- 用适当时长的 `wait_agent` 或状态通知等待结果，必要时才用 `list_agents` 核查；超时不等于失败。避免碎片化等待、重复读日志和催问状态，有实质进展、问题或阻碍时再沟通。
- 发现其他会话或用户修改时，保留外部改动，核对实际差异及受影响的实现、规范、验证和评审结论。只补充受影响部分，不自动覆盖，也不无条件重启整轮评审。需求变化造成的必要返工与重复交接应区别处理。

## 阻塞与恢复

可定位修复的失败、有依据可解决的评审分歧，继续处理。以下情况暂停受影响的工作；若阻塞整体交付，则暂停流程并向用户说明：

- 关键资料缺失、要求冲突、必要工具或测试环境不可用，且无法在现有授权内解决。
- 修复必须改变已确认计划或验收条件，或争议无法依据现有资料解决。
- 同一问题反复返工，没有实质进展，也没有新证据或可行修复路径；不设未经用户约定的固定返工次数。

Review 发现阻塞时通知主 Agent，说明对应版本、原因、已有结果和恢复条件，然后停止受阻工作。主 Agent 核对情况，必要时用 `interrupt_agent` 中断受影响的子 Agent，并确认未完成命令状态；中断 Agent 不保证后台命令终止。

主 Agent 向用户报告需要补充的信息或决定；已有授权内能解决的事项自行处理。阻塞解决后，由主 Agent 确认当前差异、有效验证和责任人，恢复受影响阶段；需要 Review 继续工作时用 `followup_task`。旧交接消息不能解除暂停。

## 完成条件

主 Agent 核对最终实际 diff，确认计划验收项已覆盖、必须修复的问题已关闭、必要验证和独立评审通过结论适用于最终代码，且没有待处理阻塞或未完成的任务。最终一致性核对以实际差异为准，不因每个小改动重复全量冻结、验证和交接。

Review 通过后，主 Agent 更新计划或交付文档的完成状态。纯状态更新只核对内容与必要格式、链接，不重新启动整轮交接或行为测试；若同时修改了功能、规格或验收要求，则按实际影响补充验证与评审。

最终简短汇报实现范围、评审和实际验证结果，以及有影响的未验证事项；区分标准测试、mock 验证、静态检查和真实环境验证。阻塞时说明当前进度、原因和恢复条件，不宣布完成。提交、推送、发布或安装同步均遵守用户授权和目标仓库入口，不由本 skill 自动扩展执行范围。
