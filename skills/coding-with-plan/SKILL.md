# coding-with-plan

## 输入与启动

执行用户在前序会话确认的 plan，不重新规划或审批，也不额外增加权限确认步骤；遵守现有授权。Plan 路径无法唯一确定时先询问，不自行选择。

主 Agent 先读取 plan、目标项目适用的 `AGENTS.md` 及其指向的开发、测试文档和模块说明；存在适用的 `CONTEXT-MAP.md` 或 `CONTEXT.md` 时一并加载。子 Agent 同样读取原文，不只依赖摘要。关键决策、验收要求和必要引用应在这些文件中能够找到。

启动前记录工作区、实现范围、评审起点和已有未提交改动，避免覆盖用户改动或混入其他任务。核对下文所需的协作工具实际可用，不能只凭 `multi_agent_v2` 配置判断；缺少必要资料或能力时按阻塞规则处理。

只创建 `coding`、`review` 两个子 Agent，不继续委派。默认继承主 Agent 的模型配置，用户另有指定时遵从指定。

两者的启动任务都包含 plan 路径、工作区、规范入口、实现范围、评审起点、已有改动说明、主 Agent 标识和本技能规则。通信使用工具返回的完整标识，例如 `/root/coding`，不自行拼接路径。

1. 用 `spawn_agent` 先创建 `review`，让其读取规范，收到实现交接后才正式评审。
2. 创建 `coding`，提供 review 的完整任务标识，直接开始实现。
3. 把 coding 的完整标识通知 review。

## 任务流程

```text
主 Agent 读取 plan 和规范，核对工作区及工具
    |
    v
创建 review 等待交付，再创建 coding 开始实现
    |
    v
[A] coding 实现或修复业务代码与测试
    |
    v
coding 自验
    +-- 普通失败 --> 定位并修复 ----------------------> [A]
    |
    | 通过，冻结本轮代码并交接
    v
review 对照 plan、开发规范和测试规范评审
    +-- 必须修复 --> 反馈问题，要求修复后重测 --------> [A]
    |
    | 通过
    v
主 Agent 核对最终实现、验证与评审结果
    +-- 需要补充实现或验证 --------------------------> [A]
    |
    v
满足完成条件，向用户汇报

任一阶段真正阻塞 --> 停止交接 --> 主 Agent 暂停并反馈
    |
    +-- 未解决 --> 保持暂停
    +-- 已解决 --> 主 Agent 明确恢复版本和责任人，恢复对应阶段
```

## 实现与评审要求

**Coding** 负责全部业务代码和测试代码，按项目规范完成实现与自验。每次返工后重新运行受影响的测试及必要检查；涉及共享行为或项目规范要求时扩大验证范围。可定位、可修复的失败继续处理，自验通过后才交给 review，评审期间停止改码。

**Review** 只读检查业务实现、测试代码和自验记录，确认符合 plan、开发规范及测试规范，包括验收覆盖、回归风险和测试有效性。必须核对实际验证命令、结果及其对应版本，不能仅凭“测试已通过”验收。复审既检查原问题是否解决，也检查修复是否引入新问题。

评审问题写明位置、计划或规范依据、影响和修复验收条件，区分必须修复与可选建议；个人偏好不能阻止通过。不得通过修改已确认计划、降低测试要求或放宽断言消除问题。

## 交接规则

- **派发工作用 `followup_task`**：coding 自验后直接交给 review；review 发现问题后直接交给 coding 修复、重测。需要回应的评审异议或补充判断也用此工具。它会启动空闲 Agent；目标仍在运行时会在消息处理节点或当前工具调用结束后收到任务，不保证等上一轮结束。
- **通知用 `send_message`**：每次交接同步简要状态给主 Agent；评审通过时通知主 Agent 和 coding。此工具不会启动空闲 Agent，不能只发通知后等待其执行新任务。
- **统一交接内容**：当前状态、实现版本、下一步责任人、变更范围及验收项；交付实现时附验证命令、结果和未验证事项及原因，要求返工时附问题清单和重测要求。
- **版本与去重**：coding 每次改动并自验后递增实现版本，如 `r1`、`r2`；评审反馈指向同一版本。任务只交接一次，主 Agent 不重复派发；接收者忽略已处理或过时消息，状态不明时报告主 Agent。
- **交接后停止上一轮工作**：同步状态后结束本轮；若有效的新任务已送达，则按最新交接处理，不能继续修改上一轮代码。
- **主 Agent 持续跟踪**：用 `wait_agent` 等待更新，必要时用 `list_agents` 核查状态。超时不等于失败，不据此重复派发；子 Agent 一轮结束也不代表整个计划完成。

## 阻塞与恢复

编译错误、测试失败、规范违规或有依据可解决的评审分歧，按现有要求继续修复或核实。以下情况需要暂停：

- 关键资料缺失、要求冲突、必要工具或测试环境不可用，且无法在现有授权内解决。
- 修复必须改变已确认计划或验收条件，或争议无法依据现有资料解决。
- 同一问题反复返工，没有实质进展，也没有新证据或可行修复路径。不设未经用户约定的固定返工次数。

1. 发现者停止交接，用 `send_message` 通知主 Agent 和对方，说明版本、原因、已尝试措施、现有结果和恢复条件，随后停止工作。
2. 主 Agent 用 `interrupt_agent` 中断仍在运行的子 Agent，核对未完成命令状态，暂停整个流程并向用户反馈。消息本身不会暂停其他 Agent，中断 Agent 也不保证后台命令已终止。
3. 旧交接消息不能解除暂停。阻塞解决后，只有主 Agent 可以明确恢复版本和下一步责任人，并用 `followup_task` 恢复对应阶段。

## 完成条件

主 Agent 核对实际 diff，确认计划验收项已覆盖、必须修复的问题已关闭、必要自验和 review 通过结论对应最终代码，且没有待处理阻塞或进行中的任务；不能只凭版本标签判断代码未变。

完成后简短汇报实现范围、评审和验证结果及有影响的未验证事项；阻塞时汇报当前进度、原因和恢复条件，不宣布完成。
