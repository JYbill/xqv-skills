# Jev 应用设计与 curl 调用

由使用本 skill 的 Agent 设计流程、组织材料和编写代码，Jev 提供其中的局部语义判断；代码负责组合结果和执行操作。仅用 curl 访问官方 HTTP API；认证直接读取当前执行进程的 `TYPESAFE_API_KEY`，无需 SDK、MCP 或独立配置文件。

## 适用场景与不适用场景

- 适合材料充分、判断标准明确的语义任务：分类与分流、从已有候选中选择、判断内容是否符合要求，以及按给定等级评分。能写成选择题，不代表适合交给 Jev。
- 能通过确定的条件、计算或数据库查询得到结果时，优先使用代码或查询，不额外调用模型。
- 可以协助设计需要资料检索、多步推理或多次判断的功能；由 Agent 和代码完成流程设计、检索及状态组织，每次交给 Jev 的判断仍须有充分材料和明确标准，不把完整的复杂决策简化成一次选择。
- 候选可能不覆盖实际情况时，增加“以上皆非”或“信息不足”选项，并明确各自含义。不要在证据不足时强制选出业务选项。
- 将结果接入自动执行前，用实际任务样本验证判断效果和错误后果，确定哪些结果可执行、哪些需要补充信息或人工复核；不单凭模型置信度决定自动执行。

## 设计与资料选择

1. 从用户需要的行为出发：应用最终展示什么、选择什么或执行什么？倒推哪些步骤需要理解语义，保留用户的技术栈和任务范围。明确任务直接实施，不强制先做方案发散；只要求调用示例时，不扩展成应用设计。
2. 将材料放入 `state`，判断含义放入 `instructions`，候选或等级放入 `criteria`。单选用 `choice`，条件是否成立用 `noul`，程度用 `score`；多标签分别判断，不能用一次单选代替。问题 ID 只供代码匹配结果，完整含义必须写进问题。
3. 每题表达一个完整、聚焦的判断，独立有用的维度分别提问，同时保留必要上下文。相同状态下的独立问题合并请求；依赖前次答案才能取得材料或构造候选的问题分阶段执行。
4. 新功能、复杂问题设计或多个判断的组合，读取 [问题设计与组合方法](references/design-patterns.md)，选择与任务相关的模式。该文件包含分支预判、候选提取、重排序、评分复用、证据核验和动态状态处理。
5. 首次构造请求时读取 [HTTP 请求与返回](references/http.md)。新集成、参数变更或字段错误，核对当前官方 HTTP API；新工作流还需查相应问题类型的指导及最接近的 cookbook。已有调用的小调整按需查阅，不重复加载无关资料。

官方在线文档是接口与模型行为的事实依据。从 [文档索引](https://docs.typesafe.ai/llms.txt) 定位相关页面；可尝试为页面路径添加 `.md`，失败时读取普通页面。索引不可用时使用参考文件中的直达链接；在线资料不可用时说明限制，使用已有资料，不编造版本相关细节。curl 任务不加载 SDK 文档。

## curl 执行

1. 区分生成命令与实际调用：仅要求示例时输出命令；要求执行时，检查 curl 可用且环境变量非空，只报告是否存在，不打印密钥。缺少密钥时请用户在执行环境中配置；不搜索其他凭据文件。桌面 Agent 的执行进程未必继承终端里新设置的变量。
2. 请求仅包含任务所需且已授权发送给 TypeSafe 的内容；合并的问题不能引用同次请求中尚未返回的答案。
3. 用 JSON 文件或带引号的 heredoc 传递请求体，通过 curl 执行。密钥只进入认证头，不写入请求体、日志或仓库；执行时关闭 shell 跟踪，避免 `curl -v` 或 trace 输出认证头。Web 应用由服务端保存凭据和发起调用。
4. 同时检查 curl 退出码、HTTP 状态及 `answers` 中每个问题的类型和结果。调用失败不能报告为模型判断成功。选中某个操作不代表已执行该操作，也不代表获得执行授权。

## 返回与失败

- 报告实际模型、问题结果和必要的概率；有需要时附 `usage`。没有真实调用时明确标注请求示例。
- `choice` 必须落在提交的候选内；`noul` 是“是”的概率，不是布尔值；`score` 按返回的 `legend` 解读，不擅自当成百分制。
- `confidence` 不等于事实正确率；业务阈值由任务确定，不统一套用固定阈值。
- 401/403 停止并报告认证或权限问题；422 修正明确的字段错误再调用。429/529 按服务端等待提示或指数退避最多重试两次；超时或连接中断说明结果未知，重试可能重复计费。

## 验证应用行为

用代表性样本检查判断如何影响最终行为，覆盖实际任务可能出现的无匹配、材料不足和不确定结果；有分支或状态变化时，检查未采用分支是否被忽略、旧结果是否仍适用。阈值和 cookbook 的演示结果不能直接当成业务标准。

失败时分别检查输入材料、问题、候选、原始答案、组合规则和实际结果，区分证据缺失、模型判断错误、代码错误与服务失败。合并或增加问题时测量实际 token 用量、费用和端到端耗时，不假设一次请求总比多阶段更合适。未实际调用时，只报告设计或静态检查结果。
