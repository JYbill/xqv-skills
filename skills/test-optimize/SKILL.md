## 目标

写测试时，优先证明真实行为，而不是重复测试准备过程。选择能提供有效信心的最小测试类型，避免只验证“测试自己写进去的数据又被原样读出来”。

## 测试类型选择

除非用户或项目规范另有要求，按下面顺序判断：

1. **单元测试**：验证纯逻辑、校验规则、分支、错误处理、本地 service 行为。除非被测对象本身就是文件工具，否则不访问真实数据库、网络服务、队列、缓存、文件系统或第三方 API。
2. **集成测试**：验证代码和真实依赖、真实框架边界能否协同工作。优先使用真实基础设施，不要 mock 掉正在被集成验证的部分。默认只读；需要写入时，测试必须拥有数据生命周期。
3. **端到端测试**：通过真实公开入口验证完整流程，例如 HTTP、CLI、消息入口或公开 SDK。使用隔离测试数据，并清理测试状态。

不要因为可以写更大的测试就写更大的测试。能用单元测试直接证明行为时，不要升级成集成测试或端到端测试。风险在装配、序列化、持久化、框架行为、外部协议兼容时，再使用集成测试或端到端测试。

## 单元测试标准

单元测试通常应该验证这些内容：

- 输入到输出的有意义转换。
- 可能被错误实现的分支或规则。
- 边界条件，例如空输入、重复输入、缺失字段、非法类型、不支持状态、超时选择。
- 明确的错误消息或失败模式。
- 和协作者的交互，但前提是这个交互本身就是承诺给调用方的行为。

避免写只证明 JavaScript、TypeScript、JSON、测试框架或测试准备代码能工作的单元测试。

### 单元测试 `it` 块注释要求

所有单元测试的每个 `it` 或 `test` 块上方都要有注释，说明测试目的和测试总结。注释要紧贴测试块，内容要短，能帮助读者快速判断这个测试保护的规则。

推荐格式：

```ts
// 目的：验证只提供成对字段的一侧时会抛出明确错误。
// 总结：缺少配对字段会触发配置完整性校验。
it("rejects incomplete paired field config", () => {
  writeInput([{ publicKey: "value" }]);

  expect(() => loadInput()).toThrow("publicKey 和 privateKey 必须同时填写或同时留空");
});
```

不要写这种空泛注释：

```ts
// 目的：测试 loadInput。
// 总结：测试正常运行。
it("loads input", () => {
  // ...
});
```

“目的”写为什么要测这个场景；“总结”写这个测试最终保护了什么行为。测试名可以是英文，但注释应该用中文描述。

### 需要拒绝的无意义断言

遇到下面这种形态时，通常要删除或改写：

```ts
const input = { name: "example", enabled: true };
writeInput(input);

expect(readInput()).toEqual(input);
```

这类测试的问题不是 `toEqual()` 本身，而是 expected 直接来自 setup。测试只是写入一个对象，再断言返回对象和写入对象一致；如果生产代码只是解析、保存或原样返回，它不能证明规则、分支或业务行为。

不要禁用 `toEqual()`。当 expected 是独立定义的、能体现归一化、转换、过滤、排序、校验或默认值规则时，`toEqual()` 是合理的。

优先改成验证规则：

```ts
// 目的：验证缺少配对字段时会给出明确错误。
// 总结：只填写一侧字段会触发成对填写校验。
it("rejects incomplete paired field config", () => {
  writeInput([{ publicKey: "value" }]);

  expect(() => loadInput()).toThrow("publicKey 和 privateKey 必须同时填写或同时留空");
});
```

如果成功路径确实重要，也只断言具体行为，不要整体比较 setup 对象：

```ts
// 目的：验证空列表会被保留为空列表，而不是被默认值覆盖。
// 总结：空列表是有效输入，会按原语义保留。
it("keeps empty items", () => {
  writeInput([{ items: [] }]);

  expect(loadInput()[0].items).toHaveLength(0);
});
```

只有当成功路径保护了明确、可能回归的行为时，才保留成功断言。如果只是镜像 setup，就删除。

## 集成测试标准

当主要风险在多个真实部分是否能协同工作时，使用集成测试。

好的集成测试应该：

- 使用真实依赖、真实框架模块、真实数据库、真实队列、真实缓存、真实文件格式或真实网络协议。
- 不 mock 掉正在被验证的依赖；否则通常会退化成单元测试。
- 清楚声明需要的环境变量或测试服务。
- 使用共享基础设施时默认只读。
- 如果必须写入，使用隔离命名、种子数据和清理逻辑。
- 断言集成边界上的可观察行为，而不是私有实现细节。

不要写“mock 了所有外部部分，然后只断言 mock 被调用”的集成测试。这通常证明的是测试布置，而不是集成能力。

## 端到端测试标准

端到端测试用于验证穿过公开边界的完整流程。

好的端到端测试应该：

- 以真实调用方的方式启动应用或入口。
- 验证完整流程，而不是内部函数。
- 使用专用测试环境、schema、命名空间、账号或临时工作区。
- 测试前准备最少必要数据。
- 测试后清理或重建状态。
- 覆盖关键链路和高风险回归，不要把所有 CRUD 分支都搬到端到端测试里。

小型校验分支优先用单元测试证明，不要用端到端测试承担这种成本。

## 断言质量检查

新增或保留断言前，先检查：

- 如果目标规则被移除，这个断言会失败吗？
- 它检查的是调用方真正依赖的行为吗？
- expected 是独立选择的，还是从 setup 对象无思考复制来的？
- 断言足够具体吗，失败时能定位回归点吗？
- 测试名称描述的是行为，而不是实现细节吗？

如果大多数答案是否定的，改写或删除这个断言。

## Mock 使用原则

mock 用来隔离被测单元，不要替代正在被验证的行为。

适合 mock 的情况：

- 单元测试中慢、不稳定、收费或与当前规则无关的协作者。
- 某个依赖调用本身就是要验证的契约。
- 为了确定性，需要固定时间、随机数或进程环境。

不适合 mock 的情况：

- 集成测试声称验证数据库行为，却 mock 数据库。
- 声称验证 HTTP API 兼容性，却 mock HTTP 客户端。
- wrapper 没增加任何行为，只 mock 内部函数并断言它被调用。

## 测试数据和命名

使用能表达规则的通用 fixture。写通用测试标准时，不要使用业务路径、产品名、客户名或具体业务故事。

推荐类似命名：

- `validInput`
- `invalidInput`
- `missingRequiredPair`
- `emptyItems`
- `duplicateItems`
- `unsupportedState`

避免把测试标准绑定到某个应用领域。

## 评审已有测试时

1. 按实际触达内容判断它是单元测试、集成测试还是端到端测试，不要只看文件名。
2. 删除或改写只比较 setup 数据和返回数据的测试。
3. 成功路径测试只在能证明归一化、转换、兼容性或必要默认值时保留。
4. 对校验和保护逻辑增加聚焦的失败测试。
5. 用少量清晰断言替代大对象快照或整体对象比较。
6. 单元测试的每个 `it` 或 `test` 块上方补充中文注释，说明测试目的和测试总结。
7. 修改后运行最小相关测试命令；只有影响共享行为时才跑完整套件。

## 使用本 skill 时的回复方式

说明测试修改时保持实用：

- 说明适合的测试类型和原因。
- 指出删除或改写了哪些无意义断言。
- 说明现在保护的是哪个行为。
- 报告实际执行的验证命令和结果。
